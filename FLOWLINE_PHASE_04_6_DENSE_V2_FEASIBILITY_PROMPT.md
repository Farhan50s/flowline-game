## 1. Product hypothesis

Flowline v1 already provides reliable small square-grid puzzles. Dense v2 should support **original tall, winding, nested puzzles** that genuinely occupy more portrait height and offer more complex geometry, without deceiving the player with decorative, non-interactive strokes.

A larger arrow count **does not automatically mean harder logic** or better touch usability. Evaluate geometry, logical dependencies, overview readability, working-zoom targeting, generator runtime, and sample diversity independently.

## 2. No-break preservation contract

1. **Do not change** the current v1 recipe semantics, `getLevel(n)` mapping, seed mixing, fixtures, score thresholds, or current campaign level data.
2. **Do not modify** the currently saved `flowline.progress.v1` data, its decoder/replayer, or settings; do not run migrations.
3. A Dense v2 board must use an explicit `procedural-v2` recipe identity. A v1 identity must never resolve to new geometry.
4. Do not yet add a Dense campaign selector or unlock progression to the shipping UI; propose the future separate namespace and opt-in structure in writing only.
5. Existing engine and immutable state semantics remain the single source of truth for actual moves. All visible paths are genuine engine paths.
6. No copied levels, visual tracing, branding, or audio from Arrows – Puzzle Escape.

Snapshot/prove hashes of critical v1 fixtures and unchanged domains before and after. Unavoidable changes must be fully justified.

## 3. Prototype scope and priorities

Work in new versioned modules such as `src/game/dense-v2/` and focused new tests. Reuse current engine validation, solver, state and deterministic PRNG where appropriate, but isolate changes from the current v1 generator.

**Priority A — Dense introduction:** Prototype a **17×29** board and test a realistically packable range around **40–55 arrows**. Treat 40–60 as an exploratory question, not a forced minimum under all geometry/quality constraints.

**Priority B — Dense challenge, only if A is verified:** Prototype around **23×37** and **60–85 arrows**, evaluating up to 90 only if generation, visual quality and touch geometry justify it.

**Priority C — Expert:** Document a possible **27×45 or 32×48, 90–120+ arrow** family; do not spend most of the prototype window pursuing it. Implement an expert experiment only if A and B are successful within bounded budgets and adequate QA time remains.

For each candidate, calculate actual cell capacity: `count × average path length <= available cells`. Packing margins/negative-space constraints reduce feasible capacity. Never overpromise density by assuming all cells are usable.

Original composition themes may include vertical ribbons, nested corridors and asymmetric islands, but no theme may generate fake arrow graphics that do not participate in gameplay.

## 4. Generator and correctness requirements

- Deterministic seed input with explicit typed bounds, documented recipe version and configuration. No clock or environment-based randomness in production geometry.
- Construct valid non-overlapping orthogonal tail-to-head paths with correct outward final segment. Explore mixed lengths (for example 3–12 cells with a small longer tail when capacity permits) and 1–6 turns only when existing load validator supports them. Do not broaden domain validation limits silently.
- Use reverse construction or another **proved-safe** constructive procedure. For each new arrow, prove an escape relative to already inserted arrows, then reverse removal order to obtain a witness.
- Validate completed candidates with unchanged `validateLevel` and the independent `solveLevel`. Replay the construction witness **and independent solution** through real `attemptMove`/`completeEscape` to `won` with no blocked moves.
- Detect construction budget exhaustion; return a **typed failure**, never an invalid success or misleading fallback label.
- Bound attempt count, proposal count, candidate count, generation work, and memory. Record rejection categories and bounded statistics. A generated success should be immutable/read-only in the same spirit as v1.
- Preserve stable output for same version/config/seed across repeated calls; test a pinned reference JSON fixture when a prototype recipe is settled. Any recipe change affecting geometry should get a new version.

## 5. Visual, difficulty, and interaction metrics

Measure and report **separately**:
- Board width/height, arrow count, occupied-cell count, capacity and occupancy %.
- Path length histogram/mean/max, bend/turn histogram/mean/max, straight-vs-bent share, head direction distribution.
- Dependency graph edge count, max dependency depth, initial safe fraction, solver trace and forced-choice stretches.
- Composition: connected or grouped visual structures, empty-band/negative-space distribution, head clustering, viewport stroke bounds, ink coverage. Do not equate cell occupancy with screen ink coverage.
- Overview cell size and stroke/head CSS pixel sizes at 320×568, 390×844 and landscape, without non-uniform stretching.
- Working zoom needed for target ~24–32+ CSS pixels per cell, and whether 4× remains sufficient.
- Hit target ambiguity and potential wrong-arrow taps under the current 44px finger contact heuristic. Ambiguity must remain **no-penalty**. If max zoom still cannot separate paths, propose a deliberate selection fallback rather than silently guessing.

Treat human difficulty as an **unvalidated hypothesis** until actual playtests. Do not recycle v1 easy/medium/hard thresholds as calibrated v2 scores without evidence.

## 7. Performance and test strategy

First validate correctness with a **small fixed corpus** (e.g. 20–30 seeds per candidate). Only if budgets and quality are acceptable, expand to 100+ distinct seeds per candidate, then a longer regression corpus as appropriate. Keep the full pre-existing test suite green throughout. Do not claim 1,000 successes unless genuinely executed.

Report success/failure rates, reasons, number of distinct layouts, proposal counts, memory considerations, and mean/p50/p95/max `generate` latency. Benchmark device and runtime must be stated.

The proposed **future** phone targets are generation p95 ~100–250ms, Canvas draw mean <6ms / p95 <8ms and hit processing p95 <4ms. They are *not* claims established by the existing desktop timings. If the prototype is slow, report it and propose Web Worker extraction rather than hiding a main-thread stall. Keep input/RAF free of procedural generation.

Test malformed seeds/options, impossible packing bounds, termination and typed failures, determinism, stable geometry, full solver and witness, immutable transitions, v1 compatibility, limited-memory/large cases, and no fake solutions. Verify that `npm run typecheck`, `npm run test`, `npm run build`, and `npm run android:sync` still pass.
